# 2026-11-11 — "understand the maps and the mobs" turned out to be a data problem

The request was to replace thousands of lines of hand-written tactics with real
math, because the model only has a superficial understanding. Measuring what the
model actually receives moved the problem twice, and neither move was the one
the request expected.

## 1. The "win rate" is a score that pays half for a draw

`data/fight_head_production.json` publishes `network_win_rate: 0.4062` with
`ci95 [0.3787, 0.4325]` over 200 matchups. The same file records **1 win, 157
draws, 42 losses**. 0.4062 is the mean of `network_score`, a four-level matchup
score (0.75 partial win, 0.5 draw, 0.25 partial loss, 0 loss), so:

    honest win rate on decided games : 1/43 = 2.33%, Wilson 95% CI [0.41%, 12.1%]
    draw rate                        : 78.5%
    mean score (what was published)  : 0.4062

A policy that draws every fight scores 0.5 and has never won one. The draw rate
is the diagnosable failure — it cannot finish — and the score hides it. New
`combat/outcome_stats.py` keeps wins/losses/draws apart, uses Wilson intervals
(the normal approximation returns [0,0] for 0/20 and [1,1] for 1/1), and scores
a stated probability with Brier and the Brier skill score against the base rate.
16 tests.

## 2. The maps were never the problem: threat is a distance threshold

`combat/map_field.py` (new) computes the map as geometry instead of describing
it: exact BFS distance (40 ms for 560x560), the client's own **directed** line of
sight, the normalised-Laplacian spectrum, and effective resistance. It is checked
against `CellMap` — the decoder the live client has actually fought with — on
every walkable origin, four movement budgets, and 300 sampled LOS pairs.

Two facts fell out of building it:

* **LOS is asymmetric.** The client's `getLine` is origin-exclusive, so
  `has_los(a,b)` never checks `a`. 2,618 of 44,800 sampled pairs disagree with
  their reverse (5.8%). A symmetric matrix would be wrong exactly when a monster
  stands on a cell you cannot see through.
* **Threat is `distance <= MP + range`.** Across 8 real maps and 3,486 cells the
  computed threat field agreed with that rule on 99.97%, with **zero** cells the
  rule called safe that were actually hit. The reason is the existential
  quantifier: with 5 MP a monster has ~40 reachable cells and at least one of
  them almost always has a clear line, so walls wash out.

So "he walks into the enemy instead of avoiding" is *not* a map-geometry failure
and no amount of map modelling fixes it. Distance is already in the encoder
(channel 6). What is missing is the other half of the comparison: **the enemy's
reach**, which the system does not have at all.

## 3. The real gap: every enemy arrives with an empty spell list

A live board (`C:/Users/sao/AppData/Local/DofusFarm/fight_boards.jsonl`, 333
boards) gives each fighter `spell_ids: []`, `spells: []`, and often `mp: null`.
`data/cache/monsters_full.json` has HP/AP/MP/resistances per grade and **no
spells**. So the decision layer is asked to avoid a reach nobody told it about.

Measured on monster 31, Blue Larva: 2 MP, casts `10198` Disabling Splutter at
3 AP, range 1-6 → **reach 8**. The character's longest spell reaches 5. There is
no distance at which that monster cannot answer, and nothing said so.

Fix in progress: `data/harvest_monster_spells.py` pulls `spells` and
`spell-levels` from `api.dofusdb.fr` (the same mirror the monster cache came
from). Provenance is checked, not assumed: 200/200 monsters matched the existing
Touch cache exactly on level/HP/AP/MP. Two traps found and pinned:
* `$limit` below the row count silently truncates whole spells (160 → asked for
  1000).
* the `$in` filter **silently drops ids as the list grows**: same 40 ids return
  39 at batch 5, 39 at 10, 26 at 20, 11 at 40. Batch size is 10 with the
  measurement in the comment.

Read side is `combat/monster_mech.py`: monster id + level in, `(min_range,
max_range, expected_damage)` out, plus `reach()` and `damage_per_turn()`. Missing
is `None`, never zero — an unknown reach read as zero marks every cell safe.

## What this changes about the plan

The reward-tuning request ("reward when not hit and do damage") was the right
instinct but aimed at the wrong input. `threat_field`/`danger_at` are now exact
and cheap, so the reward can be computed rather than tuned — but only once the
enemy's spells are in the observation. The order is: harvest → resolve board →
then the reward has something true to say.

## Correction: the bridge capture was not needed

The note above called the bridge change "the single highest-value change left".
That was wrong, and the corpus says so. The page has been sending the resolved
spellbook all along: `mobile-disguise.js` copies `spells` straight off the fighter
object (`spell_ids: spellIds, spells: fighterSpells`), and `trajectories/
fight_boards.jsonl` carries the full object with `id`, `ap_cost`, `min_range`,
`range`, `requires_los`, `max_cast_per_turn` and `effects`. No client, no
network, no C# rebuild.

What was actually missing was a reader. `combat/monster_mech.py` gained
`from_live_corpus()`, which walks the recorded boards and rebuilds the bestiary
keyed by name (the fighter object has no `creatureGenericId`, so name is the only
key that exists). `combat/threat.py` now consults it between the board's own
spell list and the level prior, as source `"corpus"`.

Measured on fight 2659:

| monster | MP | spell | prior reach | observed reach |
|---|---|---|---|---|
| Merkaptan Leader (lvl 5) | 0 | Thwack, range 10, 1 AP, LOS | 5 | **10** |
| Ayin Spyr (lvl 50) | 3 | Burst of Motivation, range 63, buff | 8 | **None** |
| Barbakle (lvl 5) | 0 | none recorded | 5 | 5 (prior) |

The prior assumed five, so the policy was told the fight was safe at a distance
the monster hits from. That is the "walks into the enemy" complaint, with a number.

**A latent bug fell out of this**: `reach()` used `pool = damaging or spells`, so
a monster whose only spell is a range-63 global buff got `MP + 63`. Ayin Spyr
would have had reach 66 and marked *every* cell on the map threatened, pricing
cover and distance as worthless. `GLOBAL_RANGE = 63` now excludes those from the
fallback, and such a monster returns `None` (unknown) rather than a fabricated
number.

**What is not trusted**: the damage scale. No recorded fight anywhere in
`trajectories/play_dofus-*.jsonl` carries a positive `loss`, so there is no
measured hit to calibrate against, and `Thwack` reads as 400 damage for 1 AP --
not credible for a level-5 monster. Reach is observed (client states range + MP);
damage stays learned/prior. Do not wire `damage_per_turn` from this table until
a damage number has been captured.

Cost: 35 ms to build the table once, 0.69 us per cached lookup.

Tests: `combat/test_monster_mech.py` 23 (1 skip), `combat/test_threat.py` 46,
`agent/test_bridge.py` 6. The corpus wiring was falsified by disabling the step:
2 tests fail, then restored.

## The learned grid policy had never ranked a plan

Found while measuring the encoder change, and it is the largest defect of the
session. Three faults sit on one seam:

1. `combat/grid_infer.py:_padded` called `grid_dataset._plans` and unpacked
   **five** values from a **seven**-tuple. Every call raised
   `ValueError: too many values to unpack (expected 5)`.
2. `_plans` is the *training* featuriser: it shuffles the candidates (so a label
   cannot be read off row order) and rejects a board whose best plan is tied.
   Even with the arity fixed, a shuffle attaches every score to a different plan
   than the one it was computed for.
3. `combat/live_policy.py:_grid_choice` read `ranked[0][1]` from a
   `(list, metadata)` tuple -- that is the *second-best* `(score, plan)` pair, not
   the best plan. So the caller would have received a tuple where a `TurnPlan`
   belongs.

`_grid_choice` wraps the call in `except Exception: return None`, so the failure
was silent: the ranker answered `None`, the policy fell through to the solver,
and `models/combat_grid/model.pkl` (30.7 M params) has never influenced a live
decision. This is the mechanical explanation of "the trained policy has never
taken a live turn" that `brain_service`'s docstring records.

Fix: `grid_dataset.plan_rows()` is the order-preserving, non-rejecting half that
`_plans` now calls; `_padded` uses it; `_grid_choice` unpacks `(order, meta)` and
takes `order[0][1]`. Verified: `rank_plans` now returns 2 ranked `TurnPlan`s on a
test board (scores 817.58 / -1193.97, best is a `TurnPlan`).

Also: `combat.test_grid_dataset` was **not in the gate's delegated list**, which
is why a dead `0.0` feature slot and this ranker could both survive. Registered.

## The encoder had no reach channel

`grid_dataset._fighters` slot 18 of 20 was a hardcoded `0.0`. The net could see
the *distance* to an enemy and never its *reach*, so a monster 6 cells away with
5 MP and range 6 read exactly like a melee one. Slot 18 now carries
`threat.reach_of(fighter) / 30`, zero for allies.

`threat.reach_of()` is the single ladder (board spells -> learned -> corpus ->
prior) so the encoder and the price cannot disagree.

Caveat, measured not assumed: a constant-zero input has no gradient, so the weight
on that slot never moved from its random init -- the term is **small, not zero**
(~0.07 on a 20-input dense layer with He init). The model does not normalise the
fighter input. So the current checkpoint sees a small perturbation it was not
trained on; it will use the channel properly only after `grid_train` retrains.

Suites: `combat/test_grid_dataset.py` 13 (was 3), `combat/test_monster_mech.py`
23, `combat/test_threat.py` 46, `combat/test_live_policy.py` 32,
`agent/test_bridge.py` 6. Both fixes falsified by reverting them (2 failures
each) and restored.

## The corpus was rejecting 96% of its own boards

The retrain could not start because every dataset on disk was 12 channels wide
(`data/combat_grid_synth/train.npz` is `(372, 560, 12)`). Guarding
`grid_train._load` with a width check was the easy half; the hard half was that
regenerating the corpus produced **159 rows instead of the 1318 the same file
once gave**.

Measured, same 156 source boards, same seed 11, same CLI:

| build | boards | actionable | tied |
|---|---|---|---|
| v2 manifest (older solver state) | 1872 | 1318 | 0 |
| today, real boards | 1872 | 87 | 1535 |
| today, 160 duel games | 783 | 75 | 699 |

Two candidate causes were eliminated by experiment, not argument:

- the corpus reach I added to `threat` -- ablating `_corpus_reach` to `None`
  changed the counts by **zero**;
- a broken danger field -- on 216 tied boards, **zero** had a tied plan that was
  strictly safer, so `danger.swing` had nothing to separate.

The ties are real. A turn's damage usually does not depend on the cell the cast
is made from, so eight plans scoring 38.90 with the same exposure is the
solver's honest answer. `_plans` rejected every such board because "a random
tie-break would teach noise". The premise was right and the remedy was
catastrophic: it discarded almost the whole corpus, which is why the ranker had
no map variety to learn from.

### Fix: a tie is a soft label

`_plans` now returns a distribution: uniform over the winning set, zero
elsewhere. `grid_train._loss` minimises cross-entropy against it, which is the
KL to "any of these is fine" when the set is larger than one. Nothing is
invented and nothing is discarded.

Result on the same file: **2954 rows** (was 159), 14 channels wide, and
`mean_best_set` 11.3 of 16 -- the honest measure of how indifferent the teacher
is. `uniform_guess_floor` (1/11.3 = 8.8%) is the baseline any reported `top1`
must beat; `top1` alone is meaningless here because picking a random member of
the winning set already scores ~70%.

Also fixed on the way: `evaluate()` was **not jitted**, so validation dispatched a
30.7 M-parameter forward one op at a time. A 16-step run with 128 rows per split
did not finish in 15 minutes, almost all of it in eval.

Caveat worth keeping: the teacher is nearly indifferent, so the student can
learn damage tiering and geometry but not much fine preference. That is a limit
of the solver, not of the trainer, and it is the next bottleneck after this one.

Suites: `combat/test_grid_dataset.py` 16, `combat/test_grid_model.py` 3,
`combat/test_live_policy.py` 32. The old
`test_tied_best_candidate_is_excluded_not_randomly_labelled` was replaced by
`test_a_tied_best_set_becomes_a_uniform_target`, which pins that mass lands on
the winners and nowhere else.

## The turn planner: an improvement operator, and the three bugs that hid it

The user's diagnosis was correct and it generalised further than the grid model:
*"you are goin soft on the nn and it stabilise very quick"*. The same criticism
applies to the whole turn planner -- it had **no improvement operator**, only a
distillation of the solver, so it was bounded by its teacher. Three papers named
the errors: Gumbel MuZero (Danihelka et al., 2022) for the improvement guarantee,
AlphaZeroES (arXiv 2406.08687) for optimising score rather than agreement, and
Value Iteration Networks (arXiv 1602.02867) for why a reactive encoder cannot
plan.

### Bug 1: the duel benchmark could never have been non-null

`duel_value.evaluate` computed `paired[0] - paired[1]`, where both terms are
*a*'s own margin -- with *a* in seat 1 and in seat 2. Their difference is **seat
bias**, which is zero by construction. Every comparison therefore returned
`p 1.0` and the verdict `no_measurable_difference`; the 20/20 split on a 0.1696
mean was manufactured by the estimator, not measured from the duels. The earlier
"honest null result" was not a result.

Fixed to the sum, `(m1 + m2) / 2`. Added a paired t-test, a seeded bootstrap CI,
`boards_differed` (the effective n -- a board where both policies play the same
plans gives exactly zero and a p-value over 400 such boards is a lie), and
`mean_seat_gap` as the diagnostic that the swap did its job.

The test that would have caught it: `BenchmarkTests.test_the_benchmark_sees_a_policy_that_only_passes`
-- solver against a policy that always passes must show `mean_hp_diff > 0.2` and
`a_better`. It fails on the old estimator, which is the point of it.

### Bug 2: the two games in a pair were not the same board

`make_duel` draws its engagement cells from the rng (`engaged_cells(cells, rng)`),
and `evaluate` advanced the shared stream between the two calls. So each game in
a pair started from a *different* position. Unbiased, but most of the variance of
the paired difference was board sampling rather than the policy. Fixed by seeding
the board and the in-game tie-breaks identically for both games, so the pair
differs only in which policy holds which seat.

### The decisive measurement: ground truth, not agreement

`scratch/rank_by_truth.py` asks the question directly. For each real board, take
the solver's k candidate plans, apply each, play the rest of the duel out with the
solver on both sides, and record the final HP differential. That is the truth
about the plan. Rank the plans by the solver's score, by the successor's HP
differential, and by the model, then compare against the truth. **Regret**
(best truth minus truth of the chosen plan) is the decision metric; agreement with
the teacher is not.

300 boards, `scratch/rbt_300.json`:

| ranker | regret | top-1 | mean rho |
|---|---|---|---|
| solver score (incumbent) | 0.0209 | 0.847 | 0.731 |
| successor HP differential | 0.0209 | 0.847 | 0.790 |
| `dv_v3`, absolute value | 0.0250 | 0.843 | 0.543 |
| `dv_rank_v1`, conditional logit | 0.0210 | 0.853 | 0.588 |
| `dv_rank_v2`, logit + residual | **0.0189** | **0.870** | 0.601 |
| blind choice | 0.0653 | - | - |

Two facts fall out of the first two rows: the solver's score and the successor's
HP differential are the *same ranker* (identical regret and top-1), so the score
has no positional term at all. And the total improvement available from re-ranking
the solver's six candidates is **0.0209 HP-differential units -- about 1% of an HP
bar**, which is why duels cannot see it.

### Why the absolute-value model lost: 93.5% of the variance is the board

Measured on 60 boards: between-board std of a board's mean outcome 0.3766,
within-board std across plans 0.0990. So **6.5%** of the target variance is
within-board, and a ranker can only ever act on that. Regressing the absolute
return spends almost all of its capacity on the offset that cancels when you rank.
That is the estimand error, and it is not fixable by optimiser or capacity.

The fix is McFadden's conditional logit: `P(p|s) = softmax_p f(s,p)`, trained on
`q = softmax(t / temp)` within a board. Adding any constant `c(s)` to every score
on a board leaves `P` unchanged, so the offset is *unrepresentable* and all
capacity goes to the 6.5% that the decision depends on. `temp` is fixed in return
units (0.08) rather than standardised per board, because standardising turns a
genuinely flat board -- plans differing only by continuation noise -- into a
confident target.

Data must be **counterfactual**: every candidate plan rolled out on the same
decision point. `generate` never did this; it played one plan per decision and
labelled every sample on a board with that board's single outcome.

Effect on regret: 0.0250 (absolute value) -> 0.0210 (conditional logit) -> 0.0189
(logit + residual). The first step moved the model from "significantly worse than
the solver" to parity; the second put it marginally ahead.

### Continuation noise is not the problem -- the signal is real

`scratch/rollout_noise.py`, 16 boards, 6 rollouts per plan under a stochastic
playout: continuation std per plan **0.0107**, std of plan means within a board
**0.0941**. So the within-board differences are nine times the noise floor and
genuinely learnable. The `rollout_truth` continuation is *deterministic*
(max |r1-r2| = 0.0000 over 12 boards, different seeds), which is why one rollout
is exact -- but a single deterministic continuation is still one sample from a
wide distribution, and that is what the stochastic probe measures.

### Bug 3: trained on turn 1, deployed on every turn

`_ranked_chunk` took `plans_for(state, ...)` at the **opening position only** and
never advanced the walk. The model learned to rank plans in openings and was then
asked to rank them at every depth of a fight.

Measured with the duel benchmark finally working. Every row below is from the
**paired** estimator except the one marked otherwise; the unpaired design inflated
small effects, which is exactly why it is superseded.

| policy | boards | mean HP diff vs solver | 95% CI | better / worse | verdict |
|---|---|---|---|---|---|
| `dv_rank_v2`, residual + MLP, openings only | 200 | -0.2646 | [-0.2848, -0.2454] | 2 / 198 | solver better |
| `dv_rank_v3`, residual + MLP, all depths | 200 | -0.1463 | [-0.1626, -0.1305] | 7 / 160 | solver better |
| residual only *(unpaired, superseded)* | 200 | +0.0229 | [+0.0105, +0.0357] | 31 / 8 | value better |
| residual only | 200 | +0.0083 | [+0.0004, +0.0157] | 33 / 7 | value better |
| residual only | 600 | **+0.0113** | **[+0.0072, +0.0154]** | **104 / 17** | **value better** |

The residual alone **beats the solver**; adding the network turns +0.011 into
-0.265. The residual carries `hp_diff`, which is meaningful at any depth, so the
damage is entirely the correction being applied out of distribution. Trajectory
coverage then cut the loss from -0.265 to -0.146 (both measured paired, so the
comparison is clean) -- right diagnosis, insufficient fix. The corpus now walks
one solver trajectory per duel and snapshots evenly spaced decision points
(`--snapshots`, default 3); verified spanning rounds 1-6, 64% beyond round 1.

The unpaired residual row is kept only to show the size of the error the estimator
fix removed: +0.0229 against +0.0083 on the same board count. It is not a result.

### Two smaller defects found on the way

- `forward(...)[:, 0]` collapsed the *plan* axis instead of the score axis, so
  every plan on a board received the same score, the softmax became uniform, the
  loss became the constant `log K` and no gradient flowed. Caught by
  `test_the_fit_learns_the_within_board_signal_not_the_offset` (top-1 fell to
  0.20). Must be `[..., 0]`.
- He-scaled output weights gave the untrained branch a std of ~0.5 against the
  residual's ~0.3, so the model did not start at the incumbent it was meant to
  improve: Spearman 0.61 at epoch 1 instead of 0.84. Zero-initialising the last
  layer makes the untrained score *exactly* `hp_diff`, which is now a test
  (`test_an_untrained_score_head_reproduces_the_hp_differential`).

Also: `np.unique(groups, return_index=True)` on the unsorted array returns
first-occurrence indices, not sorted positions; `starts` must come from the
sorted copy or the group packing silently misaligns rows with labels.

### LayerScale never opened

After 80 epochs the learned residual gains were `0.0094, -0.0213, 0.0013` -- the
three-layer net is effectively one layer. Both rank objectives plateau at the same
Spearman (0.635 / 0.634), so depth is not the bottleneck, but nothing in this
model is using its depth either.

### Widening the candidate set buys little

With `beam_width 32` and `k 30` (28 plans per board, 30 boards), the solver's
top-1 regret rises only from 0.0209 to 0.0295, and blind choice is 0.0626. The
action space is not the bottleneck either: the solver's own ranking is already
within ~0.03 of the best plan it can generate.

### The one durable positive

The residual -- plain `argmax` over the successor's HP differential, `w_score`
zeroed -- beats the solver on **104 boards to 17** over 600 paired duels,
`t = 5.4`, `+0.0113` of an HP bar. It is a **one-line change to the ranking
criterion, not a network**: the solver's composite score is a worse objective than
the HP differential its own plans produce. `combat/live_policy.py::_hp_choice`
implements it (see below).

Two honest limits. The effect is small -- 0.011 of a bar, so it is a better
tie-break among near-equivalent plans rather than a change of strategy. And it is
measured on 1v1 duels; the sum over each side generalises to multi-enemy fights
but has not been measured there.

### The margin gate does not rescue the network

`--margin` (conservative improvement: deviate only when the advantage clears a
multiple of the candidate score spread) left `boards_differed` at 164 and 159 of
200 for margins 1.0 and 2.0, against 167 unrestricted, and the mean got slightly
*worse* (-0.152, -0.155 against -0.146). So the model's high-confidence deviations
are the harmful ones, which is the signature of a value fitted to the wrong
continuation rather than of a noisy estimate.

That is the mechanism, stated plainly: the value is trained on continuations where
both sides play the solver, and the policy then deviates on 84% of boards, so it
optimises against a future that does not occur. A one-step lookahead with a
fixed-policy value is only valid while the continuation policy is the one the
value was trained on. Fixing it means policy iteration -- retrain the value on the
policy's own trajectories -- not a better optimiser, and not more capacity.

### An error of mine, caught by the audit, and the reason it matters

While adding the shipped-ranker paragraph to `resume.md` §0 I "corrected" the explanation
for `_value_choice`'s zero count from "the `_cast_cell` scan is a superset of the beam's
origins" to "the `_value_ready` gate is false". **The original was right.**
`ARCH_REASSESSMENT.md` §L.22 had already run four arms and written "So it is not the
readiness gate." I replaced a measured cause with an inferred one, in the same file I had

Reverted, and the line now carries the four-arm result plus a note that the 2026-11-11 pass
asserted the opposite -- deleting it would have hidden the fact that the file is a place
where this happens.

The contradiction turned out to be real and resolvable, which is why it was worth chasing:
`_value_choice` has **two** call sites. `live_policy.py:708` (inside `_cast_cell`, argument
`matching`) is the one §L.22 measured and it is gated by an empty list. `live_policy.py:753`
(inside `_solver_turn`, argument `plans`) is gated by `_value_ready`. Both statements were
true about different branches.

And the second gate is worse than a flag: `_value_ready` is assigned in exactly one place,
`live_policy.py:967`, on the **actor** path -- and `_solver_turn` returns before reaching it.
So in solver-first mode (the default) the flag is only ever written on a turn the solver
declined, and the next solver turn reads whatever that left behind.
