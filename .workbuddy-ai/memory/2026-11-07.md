## Conventions learned

- **A probe's own success test is a defect surface.** `inv.equip` used "a message left" as success;
  `equipItem` emitted `position: 63` (the not-equipped marker) and the loop moved on. Always verify
  the outcome field, not the send.
- **The gate asserts on source text in places.** Changing a guard's wording breaks
  `test_equip_slot_from_template`; update the assertion with a comment saying why the shape changed.
- **Fakes must use the instrumented path.** The equip test's fake pushed to its own `sent` array, so
  the handler's guard read zero; making it call `window.dofus.sendMessage` was what revealed the real
  behaviour.
- Tagged counters in `resume.md` drift on every live session and every script edit. Reconcile after
  the last run, not between runs; `$TEMP/reconcile.py` + a gate run per round works.
- `live_probe.py` in the evidence dir is the one probe helper: payload matches `executor.py`, exit 0
  = ok, 1 = refused, 2 = no client.
- The client reads `scripts/mobile-disguise.js` **at instance launch** — script changes need a
  restart, Python changes do not.

## Why a script change needs a full instance restart (measured, not guessed)

`farmengine.MaintainCdpSession` does `File.ReadAllText(disguisePath)` **once** at worker start, then
re-injects that captured string on every `Page.loadEventFired` / `Page.frameNavigated`. So:
`debug.reload` cannot pick up an edit (its own note says so), the CDP worker cannot be made to
re-read without a restart, and the bridge has **no** instance-restart route — `StopInstance` is
GUI-only (`aipanel.cs`). There is no eval-style directive either, so the handler table (a closure in
`__agentDirective`) cannot be patched from outside. Conclusion: script changes are JS-suite-verified
only until the next instance start. Candidate fix, not made: re-read on navigation with the cached
copy as fallback (`farmengine.cs` + `compile.bat`).

### Follow-up: the residual was closed the same session

- `AgentHTTPServer.max_concurrent_requests = 512` + `threading.BoundedSemaphore` taken in
  `process_request` (accept thread) and released in `process_request_thread`'s `finally`.
  Excess connections wait in the 128-deep backlog instead of reserving thread stacks.
- **First attempt was 64 and it was wrong** — the re-run of the HTTP harness reported
  "control plane stopped answering during partial-body flood": taking a slot blocks the
  accept loop, so the cap is also the number of connections answered while all are stalled,
  and 160 stalled bodies starved `/agent/health` for the full timeout. 512 keeps liveness
  (health 3 ms during the flood) and still bounds a 10k flood. Lesson: re-run the harness
  after a "fix" — the fix can trade one failure for a worse one.
- `AgentHTTPServer.handle_error` demotes `ConnectionError`/`TimeoutError` to debug. The
  159 tracebacks in the stress log were `socketserver` printing a stack for every client
  that hung up; the same abort scenario now logs 0 bytes to stderr.
- Tests (`HttpConcurrencyCapTests`, `HttpLivenessUnderFloodTests`): thread growth ≤ cap+2,
  every slot released, health <1.5 s during a 40-socket flood, and the invariant that the
  cap must exceed the flood size. Suite is 27 tests.
- Gotcha in my own test helper: reading a response until EOF measures the socket timeout,
  not the response time, because HTTP/1.1 keeps the connection alive. Parse Content-Length.

### RESOLVED: the ~4.8% "request loss" was a harness bug (11:20)

Wrote `diag_sustained.py` to re-run phase 7 with error capture. Every single
"error" is a `503` from `/brain/health` — the stress server starts without a
brain module, so `/brain/health` correctly returns `503 brain mode is off`.
The harness includes `/brain/health` as 1 of 7 GET paths; 1/3 of sustained
requests are GETs; so 1/3 × 1/7 = 1/21 ≈ 4.76% of requests correctly receive
503. Measured 4.7–4.8% matches exactly. Never was a server defect, connection
issue, or ephemeral port exhaustion. The original harness counted `status >= 500`
as "error" without distinguishing "server crashed" from "endpoint deliberately
returns 503." No fix needed; the backlog change to 128 is harmless and stays.

**All stress-test findings are now resolved.** Zero open items remain.

### Test-robustness fix (10:15)

Two tests in `test_stress_hardening.py` (`HttpErrorResponseTests`) asserted
`b'"ok":false'` — the compact orjson serialization. When orjson is absent, the
stdlib fallback produces `"ok": false` (space after colon). Fix: assert the
