## Follow-up: why the tail is unreachable (measured)

Decomposed macro_f1 0.2058 by class. It is mostly a small-sample artifact, not a collapse:
4 classes carry 3,581/3,719 rows (96%) at F1 0.83-0.94; 12 classes have support 0-3 where F1 is
binary noise; 2 classes (`fight.pass`, `fight.state`) have zero support.

The real defect is narrower: **16 of 21 tools are never ranked first on any val row.** The head
can only emit nav.goto, quest.advance, farm.start, fight.join, inv.sell. `quest.list` (37 rows),
`inv.list` (35), `state.snapshot` (29) sit permanently at **rank 2** — 101 rows, 2.7%, never
selectable.

Tested whether weight-space editing can fix it. It cannot:
- Median logit gap to the true tool is 1.9-3.4; only 6 of 101 rows are within the ±1.0 budget.
- Sweeping the bias coordinate: every value is net negative (quest.list at +1.0: recovers 2,
  breaks 41, net −39; state.snapshot: +3/−38; inv.list: +1/−8).
- Features DO separate the classes (Cohen's d up to 3.29 for inv.list, 2.09 for state.snapshot).
  So this is a training/class-imbalance problem, not a feature problem and not a weight problem.

Conclusion: do not build a new head for the tail. It needs class weighting/resampling or more
examples in `train_tool_policy.py`. The doc's "compile rules to weights" framing is irrelevant here.

## Class weighting: tested and rejected (2026-11-10)

`ai/train_tool_policy.py` already had `--class-weight {none,sqrt,inv}`; it was shipped as `none`.
Ran a controlled experiment on the *current* corpus (same seed 7, 80 epochs, only weighting
differing) so corpus drift would not be confounded with weighting. torch was installed into a
gitignored `.venv/` (769 MB) for this; the repo deliberately excludes it from shipped deps.

| run | acc | macro_f1 | ECE | reachable | gate |
|---|---|---|---|---|---|
| shipped base | 0.9043 | 0.2058 | 0.0222 | 5 | — |
| none (control) | 0.9054 | 0.2048 | 0.0160 | 5 | rejected (not significant) |
| sqrt | 0.8763 | 0.2018 | 0.0991 | 7 (+quest.list, +state.snapshot) | rejected |
| inv | 0.7671 | 0.1585 | 0.1808 | 17 (all but 4) | rejected |

Conclusion: class weighting converts "unreachable" into "reachable but wrong". `sqrt` buys 2

improve in either case. Reachability without precision is not progress. Do not pursue weighting
as the item-6 fix; it needs data (rare tools have 1-37 examples) or a hierarchical decision,
not a loss reweighting.

## Dedicated sequence policy: built, gated, promoted (2026-11-10, later)

User's call: stop patching the 42-wide head, upgrade to a dedicated model. Built
`ai/dedicated_policy.py` + a history block in `agent/features.py`.

**Architecture.** `x = [42 state features | 8 history tokens x 28]` = 266 wide.
History token = tool one-hot(21) + ok + error one-hot(5) + repeat flag. Model: state MLP
(42->128->128) + GRU(28->64) over the window, fused -> 192 -> tool logits(21) + value(1).
81,367 params. ONNX single input, two outputs, GRU + logit_scale folded in.

actions are added to the feature vector. The 42-wide vector compresses all history into
`last_tool` + `fail_streak` + one error slot.

in 100% of rows, so soft targets are the same objective minus the teacher's tie-break.
Value head on `advanced` (58.6% positive). Early stopping + temperature calibration on a
15% episode slice of TRAIN, never on val.

## 2026 literature read against our own measured failures

`docs/LITERATURE_2026.md` — six 2026 papers, each tied to a number this repo produced.
Two of them say a design choice here is wrong.

**CILA (arXiv:2610.27728, Oct 2026)** names why both logit adjustments failed: class-level
terms suppress *non-target* logits uniformly by class frequency, regardless of whether that
instance actually confuses them (Non-Target Logit Over-Suppression, `dL/dz_k = p~_k << p_k`).
Global and stratified adjustment are both class-level; conditioning on a stratum is not
conditioning on an instance. Our worst confusion pair (`nav.goto` <-> `quest.advance`, 35% of
lost gain) is exactly the shape it targets. Plug-in, ~5% overhead, our retrain is 142 s.

**ALER (arXiv:2610.00592, Sep 2026)** separates retention / rewriting / fusion, and shows
baselines fail specifically where rewriting is needed. Our GRU is a retention mechanism and
the stale stratum needs rewriting. It also explains a result I had written off: the hand-coded
`last_fresh_dims` measured *worse* (0.9172 vs 0.9204) because a hand-specified rewrite rule is
exactly what should be learned. ALER uses LSTM + slot memory + Gumbel-Softmax write + learned
fusion gate.

**ARM (arXiv:2604.03037, Apr 2026)** criticises dense absolute-progress rewards. Our `gains`
is a cummean progress *rate*. Measured over all 19,686 rows: argmax(mean progress) !=
argmax(final progress) on **1,614 rows (8.20%)**. Systematic, not noise — `quest.advance`
gain 1.000/final 1.0 vs `farm.start` gain 0.500/final **2.0**. A rate metric prefers
fast-and-shallow; on 1 in 12 rows the corpus teaches an action that does not get furthest.
Nobody wrote down that "best" means "highest average progress per step".

**MOSS (arXiv:2610.22193, Oct 2026)** — same observation admits multiple feasible actions;
deterministic policies regress to one. Our 22% tie rate is multimodality and the softmax
cannot express "either of these". MOSS also controls mode imbalance via the *source sampling
distribution*, which is the principled alternative to the logit offset that failed.

**CFGRL (NeurIPS 2026, arXiv:2505.23458)** — `pi ∝ pi_hat * f(A)`, monotone improvement. Our
soft targets are already this product form, which is consistent with the decision rule not
being the bottleneck (three post-hoc fixes failed). Also: a global `logit_scale` cannot change
argmax, so the fitted temperature affects exported probabilities, not decisions.

**AWR/IQL for agents (arXiv:2604.05808, arXiv:2602.20715)** — plain BC is the weak baseline in
this family. Our `value` head reports AUC 0.9727 and weights nothing.

**Ranked experiments:** (1) settle rate vs completion, relabel the 1,614 rows if completion,
no training needed; (2) CILA loss, ~3 min; (3) learned write gate, ~1 day; (4) advantage-
weighted BC off the existing value head; (5) generative head, last.

## Both literature experiments run; both closed negative

**#1 rate vs completion — CLOSED, my critique was wrong.** I had claimed `gains` (a
cummean progress rate) was an undocumented defect that teaches "fast-and-shallow" over
"slow-and-deep" on 1,614 rows. The choice *is* documented at `sim/tool_choice.py:112`,
and the documented claim holds and is understated: scoring by final progress leaves
**74.07%** of rows with a tied argmax (29.64% with every candidate equal) against 30.30%
and 13.53% for cummean. Switching would make three quarters of labels decided by the
tie-break instead of by the world. No change made. Procedural lesson recorded: a metric
disagreeing with another metric is not evidence that either is wrong — check the
generator's own rationale before reporting a defect.

**#2 CILA (arXiv:2610.27728) — CLOSED, rejected.** Implemented faithfully as a training
loss (`ai/dedicated_policy.py: cila_adjust`, `--cila`, `ai/test_cila.py` 7 tests,
weights from the fitting split only, bound 2.0). Paired on val: optimality -0.00081 CI
[-0.00430, +0.00269], accuracy -0.00350, macro-F1 **+0.0024**, fresh stratum
**-0.00326 CI [-0.00652, -0.00072]** (significantly worse), stale +0.00626 (ns).

The mechanism did not fire where it was aimed — the target pair barely moved
(`nav.goto`->`quest.advance` 52->54, `quest.advance`->`nav.goto` 19->20). Reason is in
CILA's own formula: it scales the penalty by the inverse frequency of the **target**
class, so it is weakest exactly when the target is frequent. Our worst confusion is
head-vs-head (`nav.goto` 23.7%, `quest.advance` 32.6%). CILA improved the tail metric it
targets and cannot help, because we are not losing gain on the tail. A method that
improves the classes we are not losing gain on cannot fix the loss.

**Cross-cutting, worth testing before a third attempt:** both interventions moved the
stale stratum up and the fresh stratum down -- obs-history stale +0.01357 / fresh
+0.00036 (flat), CILA stale +0.00626 / fresh -0.00326 (significantly worse). The CILA
case is clearly capacity reallocation. Hypothesis: the fresh stratum has less headroom
than its 0.960 suggests, and anything added competes with it.

**Next, from CILA's failure:** an explicit head-vs-head discriminative term — a margin
between `nav.goto` and `quest.advance` weighted by how much those two actually compete,
which is the opposite weighting to `1/n_y`. ~3 min to try.

**Records:** `models/cila.candidate.json`, `docs/LITERATURE_2026.md` §1 and §3 rewritten
with the measured outcomes. **Suite:** 1909 checks, 52 failed, nothing new. Shipped
artifact untouched.

## Durable memory: requirement (c) implemented, seeded, and measured

Operator's goal restated: fight strategically, get past stuck points, and **not re-solve a
learned thing every session**. That last clause is a claim about processes, so it needed a
store that outlives one.

**Built** `agent/persistent_memory.py` (subclass of `ActionMemory`): `_solutions` and `_dead`
keyed by `(objective, type, step, map)`, atomic save (`NamedTemporaryFile` + `os.replace` +
`fsync`), bounded at 4096 contexts. **Wired** into `agent/autopilot.py`: `memory_path` kwarg
(None = episodic, so tests cannot inherit a run's learning), `--memory` / `--no-memory`,
save every 40 steps and on every exit path, replay in the no-call branch via
`_remembered_call`, and `known_solution` rendered as its own line in `agent/tool_dataset.py`.
Daemon path (`brain_daemon`) passes the default file.

**Seeded** `tools/seed_memory.py` from 38 step logs: 1,216 advanced / 912 failed / 3,160 noop
applied, 4,310 read-only skipped -> 318 solutions over 73 contexts, 191 dead ends over 48.
Written to `data/learned_memory.json`.

**Holdout (the number that mattered):** seed 6 logs, score the 7th, 1,217 decided steps.

## The solver priced only half a turn, and the missing half was the damage taken

The user's report was behavioural -- "he uses spells on monsters when there is an obstacle and
instead of a line strategy to not get hit he just goes to the enemy" -- and it had a mechanical
cause: `BattleSolver`'s step score was `dealt + kill_bonus + heal + utility`. Nothing priced what
a *position* invites, so a cast from the open and the same cast from behind a wall scored
identically, and the move head (trained where distance was the only positional signal) walked in.
Evidence at the time: fight 1666 ended `loss` with **140 HP taken while three enemies were barely
touched**, and two of four enemies had no line of sight when the character decided to close.

**`combat/threat.py` (new, 39 tests).** For a cell, the damage the living enemies can put on a
fighter standing there before its next turn. Enemy profiles come from three sources in order:
its own published spells (priced through `DofusDamageCalculator`, so resists count), then a
learned per-monster table (`models/threat_model.json`), then a level prior (one hit = `level *
1.5` at range `5 + MP`). Reach is `max_range + MP` -- a monster moves and casts in the same turn.
`swing(before, after)` is capped at `MAX_PRICED_SWING = 60` and priced at `POSITION_WEIGHT = 0.45`.

**Wired where the plan is scored**, not as a post-filter: the beam pays
`-weight * swing(node.cell, cell)` on every step that changes cell, and `TurnPlan.exposure`
records the price of the cell the plan ends on. `_approach_plans` and `LivePolicy._move_dest`
break their "which cell in that direction" ties on exposure, so a walk to the same distance picks
the covered side. `LivePolicy` now emits a `position` block per decision (`exposure`, `here`, and
each enemy's damage/reach/source) -- "he walked into the open" has to be a number in the log.

**Measured, 200 boards from the live map with the learned table:** 25 plans changed, **damage
delta 0.00 (0 worse, 0 better)**, exposure **-4.03** (25 better, 0 worse). The term is a strict
tie-break: identical damage, quieter cell. It never trades damage for cover at the shipped
weight -- that is deliberate, and the failure mode it avoids is the 355 pass turns of the day
before. `LoadBearingTests` proves it is in the score and not just the report: at weight 100 the
same board refuses the cast it takes at 0.45.

**The table learns live.** `_ThreatObserver` in `combat_ai_server.py` folds each fight's message
log in before deciding (enemy cast -> life lost by me -> one sample), matched by log overlap so a
cumulative, rolling log is not counted forty times. Real rows after one fight: Marbmour 33,
Dolomanus 24, Clobberstone 21 -- **2-3x the level prior of 12**, which is exactly the factor by
which the old model under-priced every cell. `default_memory()` now re-reads on mtime: the same
process writes and reads this file, and a cache that never looked again priced the fight with the
table from before it started.

**`BattleSolver(memory=...)` is a callable, defaulting to None = level prior.** A benchmark, a
duel or a test must not change its answer because `models/threat_model.json` was filled in by a
live fight; only `LivePolicy` and `agent.executor` pass `threat.default_memory`.

## ProblemNet: which failure is this, and what fixed it

`Component.repair` is one callable per component, so every farming failure got `farm.start`
again. `agent/problem_nn.py` (new, 30 tests) is two heads over one numpy trunk (30 -> 24):
`remedy` (softmax over the repairs the agent has, trained on the attempts that *worked*) and
`escalate` (P(this attempt fails), trained on every attempt). Torch-free, JSON weights, house
style. The supervisor asks it to *reorder* the remedies a component already declares; no advisor,
no model, or no opinion all end at the old fixed repair, and a remedy the component cannot perform
can never be chosen. It records the situation when it acts and labels it on the next tick
(`data/problem_rows.jsonl`, append-only), and `ProblemMemory.fit` writes the model after
`MIN_ROWS = 40`.

## The exits were never published, and the border is the only thing left

## The retreat that walked into the enemy

`live_policy._move_score` is the tie-break that picks *which* castable cell a plan ends on,
after the actor's spell and target are already fixed: `_realize` collects one plan per
reachable cell that executes that cast and hands them here. It read the actor's own direction
codes backwards. The codes are 0 toward / 1 hold / 2 away -- stated in `MoveDirectionTests`'
own docstring and implemented that way in `_walk_action`, where approach keeps the hops with
`distance < here` and retreat the ones with `distance > here`. But `_move_score` returned
`+delta` for 0 and `-delta` for 2, so a plan asked to back off was ranked by how far it
*closed*, and a plan asked to close was ranked by how far it retreated. `max()` then picked
the cell nearest the enemy on every retreat.

This is the user's complaint, exactly: "instead of avoiding ... he just go to the enemie".
It is invisible in the beam search, which prices exposure correctly at
`threat.POSITION_WEIGHT` 0.45 per point against `APPROACH_VALUE` 0.5 per cell -- by the time a
plan reaches `_move_score` that decision has been made, and the only open question is the cell.
It is also invisible on the page, which just executes the cell it is handed.

Fixed by swapping the two branches, naming the exposure weight (`EXPOSURE_TIEBREAK = 0.01`,
unchanged in value, with the arithmetic that keeps it under a full cell at
`MAX_PRICED_SWING`), and pinning it with `PlanCellChoiceTests` (4 tests). Proven against the
old body: 3 of the 4 fail, and the retreat case reads `-3.0 not greater than -0.0` -- the
farther cell scored lower. 143 combat tests green after.
